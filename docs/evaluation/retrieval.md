# Retrieval, citation checking and Hindi/Marathi explanations (Wave 2, stream B)

> **Read this first.** Every number below comes from **SYNTHETIC, hand-labelled** query sets over
> **27 English passages** copied from clean in-repo text. The labels and the
> queries were written by **the same author as the retriever**. The **tuning set** (63
> queries) is the one the retriever's floors were chosen on, so **its figures are optimistic**.
> The **held-out slice** (20 queries) was written before the retriever was run on it and
> was not used for tuning; it is small, so treat it as a sanity check, not a measurement. None of
> this is real-world retrieval accuracy, and it says nothing about Hindi/Marathi retrieval or the
> real downloaded PDFs. **Every figure is regenerated by `python -m app.evaluation.retrieval` into
> `docs/evaluation/retrieval_results.json`; a test fails when the JSON and the code disagree.**

## What shipped

| Piece | Where | Rule it enforces |
|---|---|---|

| Limits | same | Linear-time chunker (adversarial 100k-character inputs are tested to run in under 0.5 s); document, chunk-count, chunk-size, token, query and `k` limits, loud where data would be lost (`RetrievalLimitError`), heap top-k, `Hit.quote` cut to 1000 characters. |
| Per-case index | `CaseRetrievalIndex` | In memory only; `purge()` / leaving a `with` block (also on an exception) empties every internal structure and the index then refuses documents; thread-safe; `purged` is read-only; `repr` never shows document text. Tests patch the common file-creating entry points to fail (a tripwire, not a proof). |
| Ranking | `schemesetu.ranking.rank_schemes` | Eligibility status first, relevance second, always `provisional=True`. Verdicts are copied, never changed; `schemesetu/agent.py` is untouched. Income is never used. |
| Citation check | `schemesetu.citations.verify_citation` | `supported` needs every figure in the cited span and each named scheme attributed by the span body (page titles are ignored) with figures near the right scheme when a span names several. `scheme_only`, `unsupported` and `uncheckable` are distinct; a figure written in words or with an unknown unit ("five lakh", "5L", "पाँच लाख") is `uncheckable`, never `supported`. Never raises. |
| hi/mr explanations | `schemesetu.explain_i18n` | Fixed templates chosen by scheme and the already-computed verdict, each sentence with a citation key; every checkable sentence is verified and unsupported ones are dropped; missing sources or trace steps degrade to `omitted_schemes`. | Harness | `apps/api/app/evaluation/retrieval.py` | `evaluate_retrieval(gold_rows, searcher)`; `evaluate_retrieval_dataset(corpus_rows, gold_rows, ...)` wires it to BM25 with every floor plumbed through; `build_results()` regenerates this document's figures. |

### Retrieval parameters (defaults)

`min_score=0.0` (absolute floor, off), `min_score_ratio=0.25` (a chunk's score must reach this
fraction of the sum of the query terms' idf; an absent term counts), `min_coverage=0.5` (a chunk must contain
at least ceil(0.5 x terms) of the distinct content terms, and ALL of them for 1-2 term queries, so "PAN card" does not match
"ration card"). The earlier absolute floor of 1.0 made every single-term query abstain in a 1-3 chunk index (the typical
single-document case); it was replaced because it could not be satisfied there.

### Tokenisation

Lower-case, hidden characters and ZWJ/ZWNJ removed, NFKC, Devanagari digits to ASCII, nukta dropped, chandrabindu to anusvara
(a copy of the fold in `kadi.injection._matching_view`; a parity test pins them together, the module itself is owned by
another stream and is not imported), danda as a separator. Amounts are unit-aware: "5 lakh", "5-lakh", "5,00,000" and "500000" are
one token; "1.5" and "1.50" are one token; commas are removed only inside valid digit grouping ("60,70" stays two numbers).
English, Hindi and Marathi question words/particles are stop-words (**the Hindi and Marathi lists are engineer-written,
NEEDS NATIVE-SPEAKER QA**).

## Metric definitions

Gold row: `{"id", "query", "relevant": ["<source>#<page>", ...]}`; empty `relevant` = out-of-corpus, the retriever must return
nothing. Hits are de-duplicated by `<source>#<page>` after over-fetching 5x the largest cut.

- `hit_rate@k`: share of answerable queries with at least one relevant clause in the top k.
- `recall@k`: mean over answerable queries of (relevant found in top k / relevant).
- `precision`, `micro_recall`: micro-averaged over **all** queries; any hit for an out-of-corpus query is a false positive.
- `pcra`: correctly retrieved relevant clauses / total relevant clauses; by definition equal to `micro_recall`.
- `mrr`: mean reciprocal rank of the first relevant clause (0 when none), over answerable queries.
- `abstention_rate`: share of out-of-corpus queries answered with an empty list.
- An undefined metric (zero denominator) is `None`, never 0.

## Data

`data/evaluation/retrieval_corpus_synthetic.jsonl` (27 passages) is **generated** by
`app/evaluation/retrieval_corpus.py` from the clean in-repo modules it quotes (SchemeSetu criteria text, BimaNyay clause and
letter output for fixed invented inputs, `clinical_triggers`, `tracker`, DaaviSetu readiness texts), and a test fails when the
file no longer equals what those modules produce (so wording drift is noticed; if another stream changes that wording,
regenerate with `python -m app.evaluation.retrieval_corpus` and re-check the labels). `page` is the passage number inside its
module, **not a PDF page**. The real downloaded Marathi/Hindi PDFs have corrupted text layers and are **not** used.

- `retrieval_queries_synthetic.jsonl`: 63 **tuning** queries (`"tuning": true`): 38 written close to passage wording,
  8 paraphrase / vocabulary-mismatch ("people over seventy", "salary", "pre-authorisation"), 17 out-of-corpus
  (12 share words with the corpus). Every passage that states the answer fact is labelled relevant (usually 1-5), so a passage
  the retriever finds but the label missed would count against precision; the labels were re-done after the first run, and the
  first set was mostly passage-wording queries, which inflates MRR/hit@1, hence the paraphrase additions.
- `retrieval_heldout_synthetic.jsonl`: 20 **held-out** queries (15 answerable, 5 out-of-corpus),
  written before the retriever was run on them and never used for tuning. Same author, same corpus.

Reading the first table: loosening the coverage floor raises hit rate and PCRA but lowers abstention and precision (the PAN-card
and similar out-of-corpus queries start to match); tightening it does the reverse and collapses recall. The 0.5 default was

review finding (short queries must match all their terms) rather than from maximising these numbers. Earlier figures in this
file (MRR 0.851 on 47 queries) were superseded: they came from a smaller, passage-worded query set with fewer labels and a
different floor, and are not comparable.

## What this does NOT show

- Nothing about Hindi or Marathi retrieval: there is no clean Devanagari corpus in the repo. Devanagari handling is covered only by
  unit tests (tokeniser, chunker, a tiny engineer-written Hindi corpus for abstention; NEEDS NATIVE-SPEAKER QA).
- Nothing about real documents (bills, rejection letters, scanned PDFs) or OCR noise, and nothing about speed on large corpora
  (scoring is by inverted index; only adversarial chunking time is tested).
- Nothing about an embedding/dense re-ranker: none exists (Kadi rule: dense similarity may only re-rank, never decide).
- `verify_citation` checks figures and scheme names, not meaning: "PMJAY covers citizens below 70" passes against "aged 70 and
  above" (pinned by a test). Only PMJAY and MJPJAY are recognised scheme names. A pass is "no unsupported number and no
  misattributed scheme name".
- The Hindi/Marathi explanation templates and number-word lists were not reviewed by a native speaker.
