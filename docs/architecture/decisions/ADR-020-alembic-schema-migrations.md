# ADR-020: Alembic migrations are the source of truth for the schema

## Status
Accepted (2026-10-19)

## Context
The API created its schema with `Base.metadata.create_all` at every start-up and logged (but
swallowed) any failure. `create_all` creates missing **tables** but never adds, alters or
drops a **column**, so any model change to an existing table never reached an existing
database. Several models carry comments like "nullable only so schema creation never fails on
a stray old row" — evidence of that limitation being worked around by hand.

## Options considered
1. Keep `create_all`; document "recreate your database after model changes". Loses data;
   forbidden by the transformation rules.
2. Hand-written SQL migration files plus a runner. Reinvents Alembic.
3. **Alembic**, autogenerated from the existing models, with an explicit adoption path for
   databases created by `create_all`.

## Decision
Option 3.
- `apps/api/alembic.ini` + `apps/api/migrations/`. `0001_baseline` is the exact pre-Alembic
  schema; `0002_document_jobs` adds ADR-019's table.
- Migrations run with a synchronous driver (psycopg2 for PostgreSQL — this is now the reason
  `psycopg2-binary` is a dependency; stdlib sqlite3 for SQLite). `render_as_batch` on SQLite.
- `SCHEMA_MANAGEMENT` (`app.config`) chooses start-up behaviour (`app/schema.py`):
  - `migrate` (default): upgrade to head. A database with ArogyaRakshak tables but no
    `alembic_version` is **stamped at `0001_baseline` and then upgraded** — adopted, not
    recreated, data kept.
  - `none`: change nothing; operators run `alembic upgrade head` (Kubernetes runs
    `infrastructure/kubernetes/jobs/migrate.yaml`). `/health/ready` returns 503 while the
    database is behind the code.
  - `create_all`: legacy, local throwaway databases only; refused under `APP_ENV=production`.
- The test suite keeps using `create_all` on SQLite for speed; `apps/api/tests/test_migrations.py`
  proves `upgrade head` produces exactly `app.models` (Alembic `compare_metadata` → no diff),
  that downgrade to base removes everything, that a legacy database keeps its rows, and that
  the state CHECK constraint exists in the database. CI also runs `alembic upgrade head` and
  `alembic check` on PostgreSQL 16 and repeats the round trip there.

## Rationale
Industry-standard, already compatible with SQLAlchemy 2.0, and the drift test turns "forgot
the migration" into a failing build (mutation-checked: adding a column to a model without a
revision fails `test_upgrade_to_head_matches_models_exactly`).

## Consequences
- Every model change ships with a revision: `cd apps/api && alembic revision --autogenerate -m "..."`, then review it.
- Downgrades exist for every revision but are **not** a data-recovery mechanism: dropping a
  table drops its rows. Restore from backup instead (`docs/operations/runbook.md`).
- A legacy database that predates columns added before 0001 is stamped as if it had them.
  That was already broken under `create_all`; the warning at start-up says so.

## Operational cost
Alembic (runtime dependency, used by `app.schema`). A migration step in releases when
`SCHEMA_MANAGEMENT=none`.

## Risks
`migrate` at start-up is only safe with one API process (two processes would race the
upgrade). That matches ADR-019's single-process rule; multi-instance deployments must use
`none` plus the migration Job.

## Alternatives rejected
Options 1 and 2.
