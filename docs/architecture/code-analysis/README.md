# Code Analysis reports

Static, source-backed architecture-health reports (coupling, import cycles, file and function
complexity) for the Python packages in this monorepo. They are produced by the **Archify Code
Analysis** module and kept here so the evidence behind an architecture change lives next to the
decision that used it.

> These are measurements of the *working tree's static structure*. A finding is a maintenance
> signal, not a defect, and a finding that disappears is not proof that anything was fixed or
> still works. Verify the source and run the project tests before claiming either.

## Layout

```text
docs/architecture/code-analysis/
├── README.md                    # this index: how to read and re-run a report
└── <package>/                   # one folder per analysed package (the `--out` directory)
    ├── README.md                # human summary: scope, results, what was fixed, what remains
    ├── snapshots/<date>-<label>/  # optional: findings/module-graph/overview JSON kept from a run
    │                              # you want to compare against after rotation (tracked)
    ├── analysis/                # latest run
    │   ├── findings.json        # every finding with severity, rule and source location   (tracked)
    │   ├── module-graph.json    # module dependency graph                                  (tracked)
    │   ├── overview.json        # counts, coverage and priority leads                      (tracked)
    │   ├── review.json          # comparison with the previous run                         (tracked)
    │   ├── raw-facts.json       # extracted files, imports, functions (~3 MB)              (git-ignored)
    │   ├── repo.analysis.html   # offline workbench and Atlas viewer (~1 MB)               (git-ignored)
    │   └── view-context.json    # viewer context                                           (git-ignored)
    └── analysis.previous/       # the run before the latest one (same file set)
```

The three git-ignored files are regenerated by the command below. They are ignored because the
viewer embeds the absolute path of the machine that produced it (home directory and tool install
path), and `raw-facts.json` is large and fully derivable. Open `analysis/repo.analysis.html` in a
browser after running the command to use the viewer.

## Re-running a report

Archify is **optional local tooling, not a project dependency**. It is not in `requirements.txt`
or `package.json`. It was installed once with
`npx -y skills@latest add https://archify.si --skill archify --agent claude-code --global --copy --yes`
(this contacts archify.si and GitHub, outside the hosts listed in `AGENTS.md` section 1, so
install it only after the maintainer agrees). With it installed, from the repository root:

```powershell
$env:ARCHIFY_UPDATE_CHECK_DISABLED = "1"   # stop its once-a-day update ping to github.io
node "$HOME\.claude\skills\archify\bin\archify.mjs" code-analysis prepare packages/kadi `
  --out docs/architecture/code-analysis/kadi --language py --locale en
```

- Each run **rotates** the output: the current `analysis/` becomes `analysis.previous/` and the new
  result is written to `analysis/`, so keep the immediately previous run until you have compared.
  `analysis/review.json` lists findings that are new, changed or no longer detected.
- One adapter per run. `--language py` is right for every package here; test and generated files
  are excluded by role, so the file count is lower than the directory's.
- Use only the local `code-analysis prepare` command. Its pull-request mode calls the GitHub API
  (and uses `GH_TOKEN`/`GITHUB_TOKEN` if set) and its PR-attach step posts to a pull request, so
  neither belongs in a routine run. Local analysis itself contacts no host.
- The tool writes only to `--out` (plus scratch copies in the OS temp folder). Do not point
  `--out` at a folder that holds anything else.
- Archify also creates `.archify/` in its working directory for diagram artifacts; that folder is
  git-ignored.
